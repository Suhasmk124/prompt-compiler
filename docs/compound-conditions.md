# Matching multiple invoice fields

New model-generated plans can combine conditions in one `flag_rows` or `filter_rows` node.
The LLM selects the columns, comparisons, values and AND/OR combination from the user's
instruction. The local executor applies that generated plan to the uploaded table.

For example:

> Flag invoices whose payment mode is upi and delivery city is hyderabad.

For an input with `payment_method` and `delivery_city`, the intended plan is:

```json
{
  "version": "1.0",
  "title": "Flag UPI invoices delivered to Hyderabad",
  "steps": [
    {
      "id": "read",
      "label": "Read uploaded invoices",
      "operation": "read",
      "files": ["invoice_stress_test.csv"]
    },
    {
      "id": "match_rows",
      "label": "UPI and Hyderabad",
      "operation": "flag_rows",
      "source": "read",
      "match": "all",
      "conditions": [
        {"column": "payment_method", "comparison": "eq", "value": "upi", "case_sensitive": false},
        {"column": "delivery_city", "comparison": "eq", "value": "hyderabad", "case_sensitive": false}
      ],
      "output_column": "matches_request"
    },
    {
      "id": "report",
      "label": "Export flagged invoices",
      "operation": "export",
      "source": "match_rows",
      "filename": "flagged_invoices.xlsx"
    }
  ]
}
```

This is an explanatory example, not a hardcoded plan or an automatic fallback. New plans
are always generated by the configured provider. Structured CSV/XLSX inputs use their
existing columns directly, without applying the document invoice extractor.

- `match: all` means AND; `match: any` means OR. Up to 12 conditions are supported per node.
- Flagging preserves every row and adds one combined nullable boolean column.
- Filtering removes rows that do not match. Unresolved missing filter values stop execution.
- Text equality/inequality ignore case and surrounding whitespace by default. Original
  cell contents are preserved. Explicit case-sensitive matching remains available.
- Simple existing `flag` and `filter` nodes remain compatible and use the same text defaults.
- Numeric comparisons keep the existing numeric and currency checks.
- Missing values retain nullable boolean semantics: false AND unknown is false;
  true OR unknown is true; an otherwise unresolved result stays unknown.
- Conditions and AND/OR logic can be edited under **Adjust rules & output names** without
  another model call. Changing source columns requires regeneration or an explicit JSON edit.

The compiler rejects an obvious flagging omission when the request asks for flags but
no exported report contains a generated flag column. This includes plans that discard
the flag with a later select or export an unflagged branch. The feedback strategy can
use that validation error within its existing retry budget. This is a limited action
check, not a complete natural-language correctness guarantee.

Report previews put generated flags first and show matched/unmatched/unknown counts.
Downloads preserve the workflow's output column order. Equal row counts are expected
for flagging; the added boolean column is the result. Ask to keep only matching rows
when a smaller report is desired.

After updating, restart the app and generate a fresh plan. Existing sessions invalidate
their previous plan when they observe the compiler revision change.

Verification for this change used local execution fixtures and syntax checks only.
No model requests or browser tests were performed. Live model generation is left to
the project owner.
